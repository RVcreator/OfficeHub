# Password reset and first-login repair

The current server Auth requirement takes priority over local completion markers, old completion timestamps, user-editable metadata and stale profile metadata. A required first login remains required on reload. Recovery intent is latched before deferred auth events can replace it, stays pending across a same-tab reload, and is cleared only after confirmed completion. Fresh server checks on sign-in, focus and each visible minute detect later administrator resets for existing sessions.

Password updates no longer report success for expired sessions, network errors, rejected passwords or failed finalisation. The new officehub-complete-password endpoint validates the caller, updates only that user's password through the user-scoped Auth API, and then invokes a service-only database confirmation. Auth and profile flags clear together in a transaction that checks the same reset generation; a newer reset cannot be silently cleared. This database function never receives passwords or hashes and cannot be executed by ordinary users. The old timestamp-only clearing endpoint is retired with HTTP 410.

An administrator reset starts a new reset generation and clears the old completion date in both server representations. Profile-only fallback resets are removed. New-account creation must be confirmed in Auth and starts with the requirement on the initial create call. A failed create cannot fabricate a local account, retry another provisioning endpoint or silently reset an already-existing account. Newly generated temporary passwords are returned for the administrator's current confirmation screen, without persisting them in profile or browser caches.

Deployment: validate the new migration in a rollback transaction against the actual schema, then apply it. Deploy officehub-complete-password (with its shared helper), updated admin-reset-password and admin-create-user; keep JWT verification enabled. The alternate create-staff-user source is also corrected but need not be created if unused. Retire clear-must-change-password. Pull/rebuild the frontend before using reset or first-login flows. The new client calls the new completion endpoint; the old preview cannot demonstrate this fix.

No existing user's password should be changed during automated live verification. Use mocked Auth services, disposable local fixtures, and rollback-only flag checks. The final real first-login/password-change test requires the user to enter their own password after the updated frontend is available.

Tests cover repeat resets after previous completion, first-login restores, recovery event coalescing, failed Auth/metadata/profile confirmation, stale reset generations, rejected/same passwords, expired sessions, account creation failures, cache safety and administrator handler behavior. Optional PostgreSQL integration tests require PGlite in the local Node environment.
